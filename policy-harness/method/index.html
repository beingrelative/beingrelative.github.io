A deterministic policy layer for tool-using LLM agents — method description

For the τ³-bench banking_knowledge custom submission (Qwen3.8-27B-FP8 + Policy Harness). Geunho Lee, independent researcher · beingrelative@gmail.com

What this is

We evaluated an open-weights model (Qwen3.8-27B-FP8, not fine-tuned) on τ³-bench banking_knowledge with a policy layer installed around the standard τ² agent scaffold. The layer does not learn and does not replace the model's judgement: its rule engine checks a proposed turn against declarative rules before the turn is committed, and asks the same model to regenerate when a rule is violated.

This page documents what the layer does, what it does not do, and how the reported numbers were produced. τ-bench requires custom submissions to link an implementation or methodology description; the code itself is not public.

What the layer does

The layer sits between the agent model and the benchmark's tool interface. Benchmark tasks, domain policy documents, domain tools, the user simulator, and the evaluator are unmodified.

  1. Pre-commit check. When the model proposes a turn, the layer evaluates it against declarative rules for the domain. A denied turn is returned to the same model with the violation fact and the quoted policy sentence — no suggested value, no suggested next action. The model decides what to do. The regeneration budget is 2; a turn that still violates after the budget is passed through rather than blocked indefinitely.
  2. Closed predicates only. A blocking rule may only test what can be decided by inspection: whether an event occurred, what a record's field is, whether a string is present in a tool output. Conditions that need interpretation are not enforced by the layer; they are left to the model.
  3. Verifier tools. The layer exposes tools that compute policy quantities (limits, eligibility counts, time differences) from records the agent itself fetched. The layer does not query the environment on its own.
  4. Grounding check. Before a write, each value argument must be attributable to a tool output the agent received or to the customer's words. Values that exist only in the model's own text are rejected.
  5. Context management. The layer appends derived facts after read-tool outputs and compacts the conversation view when it grows past the model's window.
  6. Auxiliary sub-calls. For extraction and classification (for example, listing the customer's requests) the layer calls the same Qwen model in isolation, with only the material needed for that one decision.

Everything the layer adds — tools, messages, denials — is visible in the submitted trajectory files.

What the layer does not do

  • It does not train, fine-tune, or adapt the model in any way.
  • It does not read hidden task goals, reference actions, or evaluator state at run time.
  • It does not decide the agent's next action. Denial messages carry a fact and a policy quotation, never an instruction or a value.
  • It does not block on open-ended or semantic conditions.

Development disclosure

The rules for banking_knowledge were developed on the evaluation tasks themselves, using per-task outcomes (rewards) and inspection of reference solutions. This submission is therefore not test-blind, and methodology.verification.modified_prompts is set to true.

To make the number interpretable we audited every rule item against its authoring evidence and sorted it into three kinds:

  • A — policy or knowledge-base citation. The rule quotes the domain documents the agent itself receives.
  • B — general rule from expert guidance. The rule states a practice a domain expert would state without reference to any particular task.
  • C — fitted to the evaluation set. The rule's form was chosen because it matched reference solutions or improved the reward on specific tasks.

Twelve items had no policy or knowledge-base citation. The audit classified ten of them as kind C and two as kind B. The submitted configuration removes all ten C items. A configuration that kept them scored higher; it is not submitted.

To check whether the authoring procedure generalizes beyond the tasks it was developed on, we repeated it on τ²-airline with a held-out split: rules were rebuilt from 30 training tasks and evaluated on the 20 remaining tasks. GPT-4o-mini moved from 31.2 to 52.5 pass^1 on those 20 tasks. In a replay of the 30 training tasks, no rule blocked a call that had succeeded. The split is not fully independent: four of the six rules reuse predicates written earlier from the policy alone, in a session that had seen one of the test tasks.

Reproducing the reported numbers

The trajectory file for each arm contains every simulation, including the layer's added tools and messages. pass^k can be recomputed from it with the benchmark's own metric code; we checked that the numbers in submission.json match such an independent recomputation. Execution was sharded one task per process across several vLLM replicas serving the same weights, with identical agent and user-simulator arguments throughout. The noise band we measured for this harness is 2σ ≈ 24 of 388 simulations. The 30-simulation gain over the no-layer arm (222 vs 192) is outside it, but not by a wide margin; gaps of a few simulations to nearby leaderboard entries are within it.

τ³-bench banking: knowing the rules and keeping them

The banking_knowledge domain of τ³-bench is 97 tasks for a bank support agent. Each task runs four times, and the board reports two rates.

Policy Harness leaves the weights, tools and policy documents alone and puts one checking step between the model's call and the real tool.

Slips at the moment of writing

We drew 32 of the 27B model's 196 banking failures at random and read each conversation to the end.

Missing knowledge was not the problem. Only one argument is wrong, so the slip is hard to see in the conversation. But once something is written to a record it cannot be taken back.

Only what the record can settle

Some policy conditions are settled by the transcript alone. We call these closed, and the ones that need a reader's judgment open. The layer blocks only on closed conditions and leaves open ones to the model.

Core idea. A check that needs interpretation would need another model, and that model makes mistakes too. If the layer blocks only what the record settles, every refusal is explained by one fact the agent can see for itself.

What happens inside one turn

This is the path one call takes from the model to the real tool.

1 · Propose

The model reads the conversation and produces its next turn. Whether that is a tool call or a message to the customer, nothing has run yet.

2 · Read

The engine loads the domain's declaration file and the transcript so far: which tools returned what, and what the customer said.

3 · Check

Seven levers each test the closed conditions they own. Most stay silent; a lever that finds a violation reports one unconfirmed fact.

4a · Pass

If nothing is flagged, the call goes to the tool with its arguments unchanged. The layer never rewrites a value.

4b · Deny

If something is flagged, the call does not run. The model gets the call, the unconfirmed fact and the policy sentence, and proposes again, within a fixed number of retries.

5 · Log

Passes, denials, injected computations and retries go to an audit log together with the tool output each relied on. The same input always gets the same decision.

Why the refusal carries no value. If the layer wrote the fix ("cancel with refund 0"), a mistake in a rule would become a mistake in an action. Returning only the fact and the policy sentence leaves the next move with the model.

Seven levers

Each lever names one slip that kept recurring in failed conversations. For every lever the panel shows what it reads and decides, and the score when that lever alone is switched off.

Moving to another domain

The engine code contains no domain words, no card and no flight. Everything domain-specific goes into one declaration file: which lookup each write needs first, which arguments must have a source, which computations are available, and which policy sentence goes with which tool.

Moving the engine built for banking to SOPBench library and τ² airline meant writing that file. Airline needed a few more generic operators, such as the hours between two timestamps, but still no domain words in the engine.

What the numbers say

We swapped only the declaration file and ran the same layer on SOPBench library and on τ²-bench airline and retail, across several models.

The gain tracks how often the model breaks closed rules. On SOPBench library all five models gained 6 to 15 points; on airline, GPT-4o-mini and Qwen2.5-32B, the two with the lowest baselines, gained 22 points or more. Airline with the 27B model, which already follows that policy, and retail, where most failures are judgment calls, barely moved.

Which levers carry the score? In three settings we switched the levers off one at a time and reran. Without the grounding lever (LB3), all three fall to or below the no-layer score. Our reading is that the computed values and policy text the other levers inject get mixed with the model's own guesses once nothing checks where a value came from.

The weight of the procedure lever (LB1) depended on how often a model broke ordering. GPT-4o-mini, with 40 calls denied for ordering, lost 9.2 points without LB1; Qwen3-8B, with 10, lost nothing.

And on unseen tasks? We split the 50 airline tasks into 30 for writing rules and 20 for testing, and rebuilt the rules from the 30 alone. On the 20 test tasks GPT-4o-mini rose from 31.2 to 52.5, and no correct action was blocked.

Where it did not help

Retail did not move for any of the four models. Most failures were judgment calls about which item or which variant to pick, and many ended because the user simulator closed the conversation early. Few were violations the record could settle.

Airline with Qwen3.8-27B stayed flat as well. The model already followed that policy, and the layer fired on a single task.

We do not count SOPBench hotel's +11.0. On 56 of 195 tasks the scorer read an OR condition as AND; fixing it leaves a difference of −0.4.

Where the layer did not help, it did not cost much either: 0 to 3 simulations lost out of hundreds, none of them traced to a wrong denial.

How we measured

What we did to keep the comparison fair, and what could otherwise have been counted as our gain.

Method 1 · serverBoth conditions on the same vLLM instancefirst reply changed on 30 / 66 tasks

Switching vLLM instances alone changed the first response on 30 of 66 SOPBench tasks and flipped 8.9% of outcomes where the layer never intervened, about the size of a real effect. Every comparison here ran both conditions on one instance.

Method 2 · attributionGains counted only where the layer intervenedsilent tasks −0.25 per run

A gain is credited to the layer only on tasks where it actually denied a call or injected a value. Tasks where it stayed silent show the noise level (SOPBench library: −0.25 tasks per run).

Method 3 · scorerThree bugs in the official SOPBench scorerreproduces 21 official FC models

The official scorer re-reads recorded calls with eval(), so JSON booleans fail and dates are evaluated as arithmetic; goal actions that return a value always score as failures; on hotel, an OR in the reference graph is folded to AND on 56 of 195 tasks. With our fixes off, the published scores of all 21 official function-calling models come out exactly, and this page reports the official numbers first.

Method 4 · simulatorThe τ² user simulator ends conversations early32 / 80 audited failures

In 32 of 80 audited failures the simulator sent "Yes" and the stop signal in the same message, so an agent that follows the policy never gets its turn to act. Every entry that uses this simulator works under the same limit.

Method 5 · disclosureThe banking rules were written on the evaluation tasks10 reference-fitted items removed

The banking rules were developed on the 97 evaluation tasks, looking at rewards and reference solutions. We audited every rule by its source: (A) a quotation of the policy the agent receives, (B) general practice an expert would state without the task, (C) a form chosen because it matched reference solutions. All C items were removed before the submitted run. This result is not test-blind; the unseen-task check is the airline held-out test.

Method 6 · boundaryWhat the layer reads at run timeno access to goals or answers

At run time the layer reads the proposed turn, the tool outputs the agent received, the policy documents the agent receives, and the declaration file. It has no access to task goals, reference actions or evaluator state.

Every number was checked against the experiment reports.
